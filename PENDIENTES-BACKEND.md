# Pendientes / dudas de backend

Nada de esto bloquea la web. No se tocó el schema de Neon.

1. **Sesión en Safari / iPhone (sin probar todavía).** Neon Auth guarda la sesión en una cookie de su propio dominio (`*.neonauth...neon.tech`) y la web vive en `santiagoasdf.github.io`: para el navegador es una cookie de terceros. Safari (ITP) y Chrome con cookies de terceros bloqueadas pueden no guardarla. Síntoma esperado: el login funciona, pero al recargar la página pide entrar de nuevo, o la contraseña se acepta y la app vuelve al login. Probar en un iPhone real apenas esté publicado. Si pasa, opciones (backend): dominio propio para Neon Auth bajo el mismo sitio (p. ej. `auth.levelupsc.cloud` + la web en `crm.levelupsc.cloud`), o un modo de token "bearer" guardado en el navegador en vez de cookie, si Neon Auth lo habilita.
2. **Alta de usuarios.** La web ya no usa código por mail: entra con mail y contraseña, y no ofrece registrarse. Igual, el endpoint `sign-up/email` de Better Auth sigue abierto por defecto, y cualquiera podría crear cuentas vacías (sin riesgo de datos, por RLS). Si se quiere cerrar: desactivar el alta en Neon Auth (`disableSignUp`).
5. **Contraseñas de Santi y Guido.** Para entrar, cada cuenta tiene que tener una contraseña cargada en Neon Auth. Una cuenta creada antes por código (OTP) puede no tener contraseña: en ese caso el login dice "El mail o la contraseña no son correctos". Hay que asignarla desde el panel de Neon Auth (o con un flujo de "olvidé mi contraseña", que la web todavía no tiene). Después cada uno la puede cambiar desde **Perfil**.
3. **Trusted domains.** Para el primer deploy confirmar que `https://santiagoasdf.github.io` sigue en la lista de dominios de confianza de Neon Auth. En local, `http://localhost:5173` (dev) y `http://localhost:4173` (preview) ya respondieron bien.
